## 2. Open decisions

This is a working register, not an attempt to predetermine the entire implementation.

Accepted rules live in the module contract. This register owns all open Operation questions, including ST1–ST5 below. The first-experiment scope and `pending` initial state are now accepted at the model level; exact schemas, transport behavior, persistence, and test results still require implementation work.

| Area | Question to resolve | Required result |
|---|---|---|
| States | `pending` is accepted as the initial state; nonterminal `unknown`, its evidence-based transitions, terminal-state immutability, and cancellation/completion outcome semantics are accepted. Remaining: [ST1–ST5](#21-lifecycle-decisions), especially complete evidence, notification arbitration, cancellation accounting, and recording/recovery | Complete transition table and invariant tests |
| Identities | Random UUIDs, scope to receiving Gecko and trusted caller, and normalized request comparison are selected for the first experiment; exact representation and production verification remain | Versioned schema and conflict rules |
| API | Start/Get/Observe semantics and the initial observation/reconnection behavior are selected for `0.1.0`; Cancel follows in `0.2.0`. Remaining: exact typed commands, response schemas, errors, and transport-independent conformance details | Transport-neutral public contract |
| Executor | Partially accepted: executors submit progress and outcomes; Core validates transitions, records state, and numbers snapshots. Remaining: work handoff, acknowledgement, notification validation and arbitration, and concrete progress/result API and errors | Executor API and error model |
| Storage | Atomic record before side effects, journal/snapshots, recovery, detailed-report retention, and safe accounting release under consumer lifecycle constraints; see ST5 | Storage API, crash-consistency model, and contract tests |
| Cancellation | Partially accepted: accepted cancellation does not override actual completion; `cancelled` requires confirmed cessation as a result of cancellation; repeated Cancel returns current cancellation status without a new stop attempt, and terminal outcomes are returned unchanged. Remaining: who may cancel, response schemas, concurrent deduplication, cancellation accounting persistence, explicit reconsideration after rejection, cooperative or forced stop, and atomic arbitration of competing executor notifications | Standalone cancellation contract |
| Composite operations | Causality, links, parent/child relations, ownership, and independent cancellation scope | Relationship model without implicit cascading semantics |
| Concurrency | Admission control, limits, queues, and conflicting actions without a global lock | Common hooks and domain conflict rules |
| Reports | Partially accepted: Core owns snapshot numbering; `reported_at` is generation time at Core. Remaining: minimum typed schema, extensions, and removal of details or artifacts | Versioned Operation Report schema |
| Transport | Minimal Zenoh Start/Get/Observe adapter is in `0.1.0`; select and validate SDK, keys, late-attachment behavior, and gaps without leaking transport details into Core | First adapter and common transport tests |
| Compatibility | Whether ROS 2 Actions or Google LRO mappings and adapters are required | Explicit compatibility targets or an explicit decision not to provide them |
| Observability | Correlation with traces, logs, and metrics without making telemetry the source of truth | Correlation context and export rules |
| Implementation | Rust on Ubuntu-24.04 in WSL and a one-process first experiment are selected. Provisional layout since November 2, 2026 (GKO-59): a root Cargo workspace with Rust crates under `crates/`; the first crate is [`operations`](../../../crates/operations/README.md), depending only on `serde` and `uuid`, with test support behind the `test-support` feature, and with the toolchain pinned to 1.99.1. The Zenoh adapter is the separate [`operations-zenoh`](../../../crates/operations-zenoh/README.md) crate (GKO-66, PR #3, in review). Remaining: a synchronous or asynchronous Executor API; whether to add CI (the repository has none) and which runner; the toolchain upgrade policy; schema format and later supported platforms | ADR after validating the minimum prototype |
| Security | Caller identity, authorization for every command, auditing, data protection, and resource exhaustion | Threat model and verifiable security gates before `1.0.0` |

### 2.1. Lifecycle decisions

| ID | Question | Status | Completed work and remaining work |
|---|---|---|---|
| ST1 | Acceptance and entry into execution | Accepted for the first experiment; broader handoff cases open | Acceptance creates one execution and visible `pending` snapshot before side effects; executor acknowledgement establishes `running`. No queue is implied. Failed and ambiguous handoff paths are covered by in-memory tests (GKO-64, `crates/operations/tests/lifecycle.rs`). |
| ST2 | Executor evidence and loss of execution knowledge | Partially accepted | A lost acknowledgement after possible handoff yields `unknown`, without redispatch; confirmation must identify the same execution token. In-memory tests show `unknown` refined to `running` or a terminal state only by an event carrying the same token. Define the complete evidence and error taxonomy, including executor loss and recovery. |
| ST3 | Concurrent, duplicate, and late executor notifications | Partially accepted | First experiment uses identified, ordered notifications: duplicates do not advance `sequence`; stale progress and conflicting terminal events are rejected without changing the snapshot, and whether they are protocol errors or ordinary rejection outcomes is open ([Z6](#24-decisions-from-gko-61)). An event rejected by transition rules consumes its number (Z6, November 8, 2026). In-memory tests cover duplicates, stale, out-of-order, invalid and conflicting events, and 32 concurrent copies of one event or two competing outcomes (one wins by lock order, GKO-64). Decide terminal-detail enrichment. Arrival order alone is not proof of actual outcome. |
| ST4 | Cancellation accounting and reconsideration | Partially accepted | Repeats do not create another stop attempt; actual completion remains authoritative. Define cancellation status fields, behavior while execution is `unknown`, responses to concurrent Cancel calls, and explicit reconsideration after a rejection. |
| ST5 | Atomic recording and recovery boundaries | Partially accepted | Acceptance precedes side effects; snapshot numbering survives normal restart. A failure before handoff ends `failed` with an infrastructure explanation (O8). A handoff result is retried, then recorded as `unknown` (O9); if that also fails, the execution stays `pending` until durable recovery (`0.3.0`). Define which state, result, snapshot, counter, and cancellation records commit together, and the recovery of a `pending` execution whose result was not recorded. |

ST1–ST5 refine the areas above rather than add a second backlog. Safe consumer-driven accounting release is also open: the deletion of an App must not become knowledge required by Core.

### 2.2. Minimum decisions before the first prototype

The following six packages are the agreed checklist for the first prototype. Their first-experiment answers and release scope are now recorded in [the model](model.md#31-agreed-first-experiment-010) at the architectural level. This approves the direction for implementation, not an untested concrete schema, selected Zenoh SDK, completed code, or a release. Finalize exact types and wire forms during implementation and validate each package separately.

| ID | Package | Accepted first-experiment decision | Remaining validation or detail |
|---|---|---|---|
| P1 | Prototype boundary and stack | Rust on Ubuntu-24.04 in WSL; one Gecko, test executor, in-memory storage; Start/Get/Observe through minimal Zenoh adapter and direct Core checks. Cancel follows in `0.2.0`. | Run the accepted scenario and failure checks; document SDK choice, test topology, and no restart guarantee. |
| P2 | State machine | Initial `pending`; confirmed handoff gives `running`, ambiguous handoff `unknown` without redispatch; terminal outcome needs authoritative evidence. | Test transitions and invariants; finish ST2–ST3 evidence and arbitration details. |
| P3 | Public API | Start has request identity, type, target, and typed parameters; Get returns latest full snapshot or explicit unavailability; Observe supplies current snapshot and later updates with cursor and gap disclosure. | Specify concrete types, errors, serialization, and Zenoh mapping; verify late attachment and reconnect races. |
| P4 | Identity and retry | Random UUIDs; retry scoped to receiving Gecko and trusted caller; normalized type, target, and typed parameters determine content equality; concurrent retries create one execution. | Verify normalization and conflict behavior; validate production identity/security and restart behavior later. |
| P5 | Executor contract | One assigned test executor, execution token, separate acknowledgement, identified ordered notifications, Core validation/numbering, duplicate suppression, stale/conflicting event errors. | Finalize event types and competing-notification behavior in code; cancellation interaction follows in `0.2.0`. |
| P6 | Accounting and trust | Atomic in-memory request mapping, operation record, and initial snapshot before handoff; trusted caller context, authorization point, and recorded decision; restricted permissive test policy. | Verify failed-commit behavior; durable accounting, persisted audit, and recovery follow in `0.3.0`; full security gate remains for `1.0.0`. |

The six packages map to the existing areas and ST1–ST5; they do not create a second set of rules. They settle the first-experiment direction while leaving wider lifecycle and implementation questions open with validation steps. In-memory storage does not satisfy or waive the target contract's durable retry and normal-restart guarantees. A permissive test policy does not establish production security; trusted context, authorization, and audit responsibilities remain governed by [security](security.md).

The first-experiment scope and checks are accepted at the model level. Before implementation is considered validated, concrete types, Zenoh mapping, and contract tests must demonstrate the stated behavior. Observe is in `0.1.0`; Cancel is in `0.2.0`. Broader integration, persistence, and security gates remain open independently.

### 2.3. Choices raised by the Zenoh spike (GKO-60)

The [GKO-60 spike report](../research/zenoh-spike/REPORT.md) measured a Zenoh `1.10.2` mapping on one host. Farhat decided these choices on November 7, 2026 under [GKO-61](https://linear.app/hakalem-echo-team/issue/GKO-61/010-decide-api-and-executor-evidence); the decisions, rejected alternatives, and deferred questions are in [§2.4](#24-decisions-from-gko-61). Everything else in the report is implementation detail under the accepted rules.

| ID | Question | Options | Spike recommendation and evidence | Status |
|---|---|---|---|---|
| Z1 | Observe mapping for `0.1.0`; fixes the observation address returned by Start | (a) subscribe-then-Get on a snapshot key plus liveliness-triggered Get repair; (b) streaming query with Core-side atomic attach and `after=<sequence>` resume; (c) both | (b), keep (a) as a measured fallback. Both have 0 missed terminals in attach races. Across link cuts (b) needs no extra signal, while plain subscribe-then-Get never learned a terminal published during the outage. (b) bounds a slow observer at Core and ends it with `lagged` instead of blocking the caller session. Report §Observe | Decided: (b), November 7, 2026 ([§2.4](#24-decisions-from-gko-61)) |
| Z2 | zenoh-ext Advanced pub/sub (`unstable` feature) before `1.0.0` | Allow for `0.1.0`; defer | Defer: the transport cache holds per-publisher samples rather than Operation `sequence`, and the model forbids relying on transport history | Decided: defer, November 7, 2026 ([§2.4](#24-decisions-from-gko-61)) |
| Z3 | Channel for typed errors | Typed `Ok` replies; Zenoh `reply_err` | Typed `Ok` replies for every Operation outcome, including invalid input. The client treats every Zenoh `Err` reply, zero replies, or a closed stream as "no answer" and retries safely. Zenoh's own `Timeout` is an `Err` with `zenoh/string` locally and default encoding when routed | Decided: typed `Ok` replies, November 7, 2026 ([§2.4](#24-decisions-from-gko-61)) |
| Z4 | Number spelling in retry comparison | Spelling-sensitive (`1` ≠ `1.0`); canonicalize numbers | Spelling-sensitive for `0.1.0`, documented in the request schema; revisit with the typed parameter schema | Decided: spelling-sensitive, November 7, 2026 ([§2.4](#24-decisions-from-gko-61)) |
| Z5 | `not_found` versus `unauthorized` on Get and Observe | Indistinguishable (anti-enumeration); distinct as P3 says for invalid input versus unauthorized | Indistinguishable for operations the caller may not see. Invalid input stays a distinct typed error. Needs Farhat because it refines P3 | Decided: indistinguishable, November 7, 2026 ([§2.4](#24-decisions-from-gko-61)) |
| Z6 | Executor event identity (P5 / ST3) | (`token`, contiguous `event_seq`) assigned by the executor; Core-assigned ids; content hashing | (`token`, `event_seq`). Same identity and content is a duplicate without a new snapshot. Same identity with other content is stale. A skip is out of order. Another terminal outcome conflicts, and the same terminal outcome changes nothing. ### 2.4. Decisions from GKO-61

Recorded from Farhat's answers on November 7, 2026. Rules that are not in this table stay as the model states them. Alternatives marked "recorded" are kept for reference and are not implemented in `0.1.0`.

| ID | Decision | Rejected or recorded alternatives | Rationale and deferred questions |
|---|---|---|---|
| Z1 | Observe uses a streaming query with Core-side atomic attach and resume after `sequence` (option b) | Subscribe-then-Get with liveliness-triggered repair (option a) is recorded as an alternative, not implemented | The spike found both at 0 missed terminals in attach races, but only (b) learned a terminal published during a link cut without an extra signal; (b) also bounds a slow observer at Core and ends it with `lagged`. Measured evidence: [report §Observe](../research/zenoh-spike/REPORT.md). |
| Z2 | Defer zenoh-ext Advanced pub/sub (`unstable`) to before `1.0.0`; not in `0.1.0` | Allowing it in `0.1.0` | Its transport cache holds per-publisher samples, not Operation `sequence`, and the model forbids relying on transport history. |
| Z3 | Typed `Ok` replies carry every Operation outcome, including invalid input. A Zenoh `Err` reply, zero replies, or a closed stream means "no answer", and the client retries safely | Zenoh `reply_err` for Operation errors | Keeps Operation outcomes typed and separate from transport failures. Retry safety follows [P4](model.md#31-agreed-first-experiment-010). |
| Z4 | Retry comparison is spelling-sensitive for `0.1.0` (`1` ≠ `1.0`), documented in the request schema | Canonicalizing numbers now | Revisit with the typed parameter schema. |
| Z5 | An operation the caller may not see and a nonexistent operation return the same unavailable response; invalid input stays a distinct typed error. [P3](model.md#31-agreed-first-experiment-010) is corrected accordingly | Distinct unauthorized and not-found responses | **Deferred:** when production authorization is added (before `1.0.0`), reconsider whether unauthorized access should get a distinct response, and record the trade-off then. |
| Z6 | Executor event identity is `(token, event_seq)`, with `event_seq` assigned by the executor and contiguous per token. Core handling, confirmed by Farhat on November 7, 2026: same identity and content is a duplicate, with no new snapshot; same identity with other content is stale and is rejected; a skip is out of order and is rejected until the missing number arrives; a different terminal outcome after a recorded one is a conflict and is rejected; the same terminal outcome sent as a new event changes nothing; progress before acknowledgement is an invalid transition; an unknown token is rejected. Simultaneous `succeeded` and `failed` on one `event_seq` resolve by Core lock order; that outcome is not deterministic for the executor. Consumption, decided by Farhat on November 8, 2026 (option B): an event that passes the number check but is rejected by the transition rules (`InvalidTransition`, `ConflictingTerminal`) consumes its `event_seq`. `last_event_seq` advances, no snapshot is created, and the event and its rejection are logged. The same identity and content returns the same rejection, even if the state has changed since; other content on that number is stale. A skip still consumes nothing and is out of order. Rationale: rejections repeat deterministically; one rejection no longer blocks every later event; an executor can pipeline numbers; a progress sent before `running` is dropped, and the next progress supersedes it. | Core-assigned event IDs; content hashing; rejections consume nothing (the earlier rule, which blocked every later event after one rejection) | **Open:** whether stale and conflicting notifications are protocol errors (P5 wording) or ordinary rejection outcomes (`Stale`, `ConflictingTerminal` in the spike); terminal-detail enrichment remains under ST3. |

### 2.5. Implementation choices from GKO-64, GKO-65 and GKO-66

Made while implementing Get, Observe, and the Zenoh adapter in `crates/operations` and `crates/operations-zenoh` under the accepted rules (P3, Z1, Z5, model §3.1 and §6). None changes an accepted rule; they fill details the rules leave open. Farhat confirms or corrects them at GKO-69. O8 and O9 come from the PR #3 review and were decided by Farhat on November 8, 2026.

| ID | Choice | Alternatives | Reason |
|---|---|---|---|
| O1 | Only the subject that started an execution may Get or Observe it; every other caller gets the same `unavailable` as for a missing execution (Z5). | Any authorized caller; a per-execution access list | The first experiment has one trusted caller scope and no sharing rule. Production authorization is a `1.0.0` gate ([security](security.md)). |
| O2 | An `after_sequence` newer than the latest snapshot is typed invalid input; `0` means "holds nothing", like no cursor, and claims no gap. | Treat a future cursor as up to date; clamp it | A future cursor means the observer's state is inconsistent with this Core (for example after a lost record), which it should learn rather than be hidden. |
| O3 | A report released by retention stays unavailable to Get and Observe and ends open streams; the request mapping, state and `sequence` counter continue. | Let later snapshots make the report readable again | Matches the model: deleting a report does not delete accounting or reset numbering. Retention periods stay a separate decision. |
| O4 | Observe returns `current: None` when `after_sequence` already equals the latest, and returns no stream for a terminal execution. | Always return the latest; keep a stream open until closed | Suppresses redelivery of a snapshot the observer holds; a terminal snapshot is final. |
| O5 | The Observe query replies with frames: `response` (the typed attach outcome), `snapshot`*, then `end` with a reason (`terminal`, `lagged`, `lease`, `unavailable`, `closed`). A non-attached outcome is the only frame. A stream ends with `lease` after 20 seconds by default and clients resume. | No lease; one reply per snapshot without a typed first frame | A typed first frame keeps Z3 for Observe; a lease bounds streams of observers that vanished without a closing signal. |
| O6 | The adapter applies one configured caller subject to every request (`ServerConfig::caller`); the request body never carries identity. | Derive the subject from Zenoh authentication | P6 allows adapter-supplied trusted context in the restricted test deployment; Zenoh authentication is not validated yet and production identity is a `0.5.0` and `1.0.0` gate. |
| O7 | The server hands a created execution to the executor before replying to Start, and answers each Start on its own thread; at most 64 Observe streams are served at once. | Reply first, then hand off; unbounded streams | A lost or late reply does not change the execution, which the retry returns; the cap is a minimal guard, not the resource protection planned for `0.5.0`. |
| O8 | A failure before handoff ends the execution as `failed`. Farhat decided this on November 8, 2026. It covers an execution record that cannot be read before handoff and a dispatch that Core abandons because the executor is unavailable. The explanation says the execution could not be handed to its executor and that nothing reached the executor. Core uses a separate path, not `Handoff::Refused`, whose explanation says the executor refused. | Keeping the execution `pending`; reusing `Handoff::Refused`, which would report an executor refusal that did not happen | Recorded on November 8, 2026. The failure is an infrastructure failure, not a proven executor outcome, so it is not a Refused handoff. `DispatchError::Unavailable` and `Acceptor::abandon` implement it. |
| O9 | If the executor was reached but its handoff result cannot be recorded, Core first retries the same result (`RECORD_ATTEMPTS`, three in total), then makes one last write: an acknowledged result is recorded as `Handoff::Ambiguous` (the execution becomes `unknown`, and nothing is redispatched), and a refusal is tried once more as it is, because a proven refusal is never downgraded to `unknown` (a refusing executor sends no later events, so `unknown` would never resolve). If that also fails, the execution stays `pending`, and the caller gets `DispatchError::Unrecorded` with the executor's result. Farhat decided this on November 8, 2026. Recovery of such a `pending` execution is not built; it waits for durable recovery (ST5, `0.3.0`). | Dispatching again; leaving the first failure unhandled; recording `unknown` immediately without retrying the same result | Retrying the same result handles a short storage failure without changing what the executor reported. `Unrecorded` is a known limit: an in-memory process that cannot record a result keeps a `pending` execution until it restarts, when everything is lost anyway. |

## 3. Current status

- The module boundary is accepted.
- The active common contract is owned by [Operation model](model.md), with security requirements in [security](security.md).
- Accepted model rules and explicitly open implementation details coexist in the module specification.
- Uncertainty transitions and terminal-state immutability are accepted at the model level; the full state machine remains incomplete.
- Cancellation/completion outcome semantics are accepted at the model level; atomic arbitration and cancellation response details remain open.
- Repeated and late Cancel semantics are accepted at the model level; response schemas, concurrency, persistence, and reconsideration after rejection remain open.
- Core authority over state validation, recording, and snapshot numbering is accepted at the model level; executor notification and arbitration details remain open.
- The first-experiment direction, including Observe and minimal Zenoh, and the working release order are accepted at the model level. A Rust build and test harness skeleton was added on November 2, 2026 (GKO-59); Start, Get, Observe, the Zenoh adapter, and their tests followed in GKO-64 to GKO-66 below.
- November 2, 2026: the GKO-60 Zenoh `1.10.2` spike measured Start/Get/Observe mappings, executor event arbitration, reconnection, and slow observers on one host ([report](../research/zenoh-spike/REPORT.md)). Its consequential choices are Z1–Z6 in [§2.3](#23-choices-raised-by-the-zenoh-spike-gko-60). Farhat decided them on November 7, 2026 ([§2.4](#24-decisions-from-gko-61)). The P3 error rule and the Observe mapping in the model were updated to match. Z6 handling rules are confirmed; the error-classification wording for stale and conflicting notifications remains open.
- GKO-64: Core issues execution tokens, records handoff results, and arbitrates executor events with Core-numbered full snapshots in memory, per Z6. Stale and conflicting events are typed rejections; since November 8, 2026, an event rejected by transition rules consumes its number (Z6). An `event_seq` of 0 is `InvalidEventSeq` and consumes nothing; an execution id with no record is `UnknownOperation` (`record_handoff`, `abandon`, `DispatchError::UnknownOperation`), distinct from `UnknownToken`. No Cancel, durable storage, or authenticated executor identity exists; the Zenoh path is GKO-66. Dispatch failures follow O8 and O9 in [§2.5](#25-implementation-choices-from-gko-64-gko-65-and-gko-66): a failure before handoff ends `failed`; a result that cannot be recorded is retried, then `unknown`, and otherwise stays `pending` (`DispatchError::Unrecorded`) until durable recovery.
- GKO-65: Core answers Get with the latest retained full snapshot and attaches Observe under the lock that publishes every snapshot; an observer that was dropped is removed at the next attach or publication of its execution, so a final publication cannot fall between reading and subscribing (300 rounds in `tests/observe.rs`; a deliberately broken attach order fails it). Resume by `after_sequence` suppresses redelivery and discloses a gap while still delivering the latest snapshot; a slow observer is ended as `lagged` without blocking Core. Choices O1–O4 in [§2.5](#25-implementation-choices-from-gko-64-gko-65-and-gko-66) await confirmation. The single publication lock is an in-memory limit.
- GKO-66 (on PR #3, in review): the [`operations-zenoh`](../../../crates/operations-zenoh/README.md) crate maps Start, Get, and streaming Observe to Zenoh `1.10.2` under Z1 and Z3, with an adapter-configured trusted caller, an in-process executor, and a client with explicit `request_id` reuse and resume by `sequence`. `make demo` and its test passed on one host over loopback, including a lost Start reply with retry and observation across a cut link; the full evidence and limits are in the crate README. Choices O5–O7 in [§2.5](#25-implementation-choices-from-gko-64-gko-65-and-gko-66) await confirmation. Multi-host, multi-hop, half-open links, Gecko restart, and load are not measured; identity is configuration, not authentication.
- Exact schemas, SDK choices, transport guarantees, and later release contents remain subject to experiments.
- November 1, 2026: common design migrated from Mesh / App into Operation; consumer requirements remain in domain documents. Historical links above record provenance, not contract authority.

The next substantive result is to finalize the first experiment's concrete API and event types, implement the selected path through Zenoh, and evaluate the six [prototype packages](#22-minimum-decisions-before-the-first-prototype). The accepted model decisions must be corrected if experiments disprove them.
