# Mesh / App: временный план завершения архитектуры

Версия плана 0.14 · 18 октября 2026 года

**Основание:** [архитектурная модель Mesh / App, версия 0.27](1-mesh-app.concepts.ru.md) и [Gecko / Axis, версия 0.9](2-gecko-axis.ru.md). Это временный рабочий список; он не заменяет предметные разделы и не означает принятия будущих решений.

**Опора для дальнейшей работы:** [Planner-Driven Build, §6.1](1-mesh-app.concepts.ru.md#61-build-planner-driven-build). Planner непосредственно вызывает участников, выбирает следующие действия и оценивает совокупный результат подготовки. Участники сообщают результаты и готовность, проверяя допустимость конкретных запросов. Build — процесс, а не операция Coordinator; отдельного исполняемого Build Plan и обязательного общего Build Report нет. Проверка перед Activation остаётся отдельным контрактом.

**Текущий шаг согласования групп 6, 3 и 5 с Planner-Driven Build завершён.** Смысл Build и оценка подготовки Planner закреплены в §6.1. В §4.2 отменена универсальная сериализация App; атомарная проверка ревизии Authority и предметная допустимость вызовов сохранены. В основном документе исправлены зависимые формулировки обязанностей, подготовки Blocks, наблюдения готовности, восстановления и идентичности операций. Обязательное дерево с Build в корне и исполнение шагов подготовки Coordinator исключены. Отдельные контракты Activation, общей очистки и действительно составных операций сохранены; их оставшиеся вопросы перечислены в таблице.

Возвращаемся к остальным вопросам этого же плана. Перечень найденных противоречий использован как список мест для правки, а не как отдельная очередь решений. Новые форматы API и дополнительные механизмы в этом шаге не вводились.

**Цель:** закрыть значимые решения уровня Mesh / App, затем провести ревизию документа. Группы ниже сохраняют номера из обсуждения; вопросы, пересекающиеся между разделами, рассматриваются вместе. В группе 6 модель закреплена; остальные группы остаются открытыми или частично решёнными.

| № | Группа решений | Что нужно определить для первой версии | Где фиксировать | Статус |
|---|---|---|---|---|
| 1 | Фиксация решения и перезапуск App Authority | Принято: новая ревизия описания App принята после надёжного локального сохранения; после обрыва создавший App Gecko публикует ту же ревизию и решение без повторного запроса. Осталось определить механизмы хранения, подтверждение публикации, завершение операции, правила остальных решений и возвращения участников | §4.2, §7.1, §7.3, §8.3 | Частично решено |
| 2 | Сохранность идентичности операций и запросов | Принято: связь запроса с операцией сохраняется до предметных действий; после обычного перезапуска повтор возвращает прежнюю операцию без второго выполнения или возобновления. Неизвестность относится к конкретной операции и не блокирует весь App. Учёт принятых изменяющих запросов хранится весь срок существования App независимо от подробных отчётов. Автоматическое восстановление полностью утраченного учёта исключено из первой версии. Осталось определить механизмы хранения и восстановления сохранного учёта, поведение после удаления App, сроки учёта остальных запросов, хранение отчётов и восстановление `sequence` | §8.2, §8.5–8.6, §7.3 | Частично решено |
| 3 | Конкурирующие операции над App | Закреплено в §4.2: универсальная сериализация операций App отменена. Planner отвечает за выбор вызовов; система не обязана исправлять его противоречивые намерения. Допустимость конкретного запроса проверяет принимающая сторона по своему контракту. Атомарная проверка ревизии Authority сохраняется. Вопрос текущего шага решён; предметные ограничения, подтверждения завершения, восстановление и конкретные регулирующие обязанности Coordinator остаются открытыми | §4.2, §6.1, §6.4–6.5, §7.3 | Частично решено |
| 4 | Изменение и остановка работающего App | Что происходит с текущим исполнением при подготовке следующей ревизии; явная остановка обработки отдельно от отмены операции | §6.5, §7.2–7.3 | Открыто |
| 5 | Итог составной операции при частичном выполнении | Закреплено в §6.1: совокупный результат подготовки оценивает Planner, который может сформировать сводку для пользователя. Обязательного общего Operation Report и системного `state` Build нет; фактические результаты отдельных вызовов сохраняются. Различение ошибки и неизвестности, отсутствие автоматического отката и явная очистка сохранены. Осталось определить общие итоги и дальнейшие действия для действительно составных операций, отмены и очистки | §6.1, §7.3, §8.2 | Частично решено |
| 6 | Вход и результат Build | Закреплено в §6.1: Build — процесс подготовки выбранной ревизии App через отдельные вызовы Planner участникам. Формальное описание композиции задаёт App Revision; последовательность подготовки выбирает Planner, отдельного Build Plan нет. Каждый вызов имеет свой результат; достаточность совокупной подготовки оценивает Planner без обязательного Build Report Coordinator. Внутренние проверки определяют участники; перед Activation выполняется отдельный запрос готовности. Конкретные схемы и контракты предметных вызовов уточняются в нижних слоях | §5.1, §6.1, §6.3 | Решено на уровне модели |
| 7 | Область Postinit | Какие Gecko входят в рассматриваемый набор; влияние заблокированного или ушедшего Gecko на этап и использование доступных участников | §2.3 | Открыто |
| 8 | Доступ к прикладному результату App | Граница API данных и подключения представлений; отличие результата видеообработки от Operation Report, описывающего выполнение операции | §4.4, §6.5 | Открыто |

**Порядок продолжения:** текущий шаг согласования групп 6, 3 и 5 завершён. Возвращаемся к оставшимся вопросам групп 1–5, затем продолжаем группы 7–8. Исходный порядок 3 → 1 → 2 → 5 → 6 → 4 → 7 → 8 остаётся ориентиром с учётом уже закреплённых решений; первые пять групп по смыслу (1–5) наиболее существенны для корректности при конкуренции и сбоях.

Для каждой группы фиксируем правило поведения и границы первой версии в основном документе, сужаем соответствующие открытые вопросы и обновляем статус в этом плане. Не считаем решение принятым только потому, что приведён пример или предложена схема.

**Отложенная конкретика:** точные типы и JSON-схемы остальных полей, коды ошибок, имена этапов, численные тайм-ауты и размеры кэшей; ключи Zenoh, QoS и backend; методики измерения ресурсов, требования Points, реакции политик Line; каналы оповещений и подробные форматы истории Observer. При этом поведение после утраты `request_id` и границы гарантии повторов относятся к группе 2, а не откладываются как простой параметр хранения.

**После восьми групп:** проверить сквозной сценарий «обнаружение → подготовка → готовность → Activation → прикладной результат → изменение/ошибка → явная очистка». Затем провести ревизию: устранить повторы и противоречия, убрать решённые вопросы, явно отметить требования к нижним слоям, детали реализации и направления будущих версий. Новые механизмы при ревизии без отдельного обсуждения не вводить.

**Условие завершения плана:** у восьми групп есть согласованные правила или явное решение об исключении из объёма первой версии; сквозной сценарий проверен; основной текст и открытые вопросы согласованы между собой. После этого временный план можно удалить отдельным изменением.
