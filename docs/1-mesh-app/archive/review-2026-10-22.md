# Mesh / App: Text Review of October 22, 2026

> Historical material from the preceding stage, before implementation scope was split in Mesh / App revision 0.43. Earlier references to the “first version,” Observer timing, and subsequent work order do not define the current plan. Active version boundaries are in [Mesh / App](../model.md); the current cycle and separate return questions are in the [progress document](../../development-cycle.md).

The main Mesh / App text, change history, and related Russian documents were reviewed. The goal was to find outdated statements conflicting with decisions already accepted. Architectural incompleteness, undocumented scenarios, and possible future improvements are outside this review's findings.

The previous analysis has been replaced: comments about Activation / Stop ordering, revision transitions, Stop recovery, resource storage, late acknowledgments, and App deletion did not demonstrate outdated text and were mistakenly included. They do not form a backlog required before 1.0.0.

## Confirmed Conflicts Between Old Text and Accepted Rules

Every item below was corrected according to an existing rule, without choosing new architecture.

| Location | Outdated wording | Existing rule it conflicted with | Correction |
|---|---|---|---|
| Mesh / App, introduction to §6 | “Names of final states ... remain open” | [§8.2](../model.md#82-operation-report-core) defines `running`, `succeeded`, `failed`, `cancelled`, `unknown` | Types, domain transitions, and transport keys remain open; `state` values are identified as defined |
| Mesh / App, §4.4; Gecko / Axis, §3.6 | “Every request performs the check again”; “A repeated invocation creates ... a run” | [§8.2](../model.md#82-operation-report-core): retrying an accepted request with the same `request_id` returns the previous operation | Both documents explicitly distinguish a new request from retrying a previous one |
| Mesh / App, §8.2; Gecko / Axis, §3.4 | The effect of an Init blocker on collection completion is called a “working hypothesis”; Axis still calls its effect on Postinit “undefined” | [§2.3](../model.md#23-discovery-and-axis-work): a necessary blocker prevents declaring completion; overall Postinit for the selected set has not been reached | Wording was aligned with the rule accepted at the time; D2 later revised it. Domain checks and formats still require lower-level refinement |
| Mesh / App, §5.1; glossary, §1, §1.1, and App row | Building or selecting options is attributed to Gecko | [§4.1](../model.md#41-app-responsibilities): the Planner is external; a separate Planner implementation inside Gecko is not required | Gecko exposes facts and APIs; the external Planner builds options |
| Glossary, introduction | Lists “Init, Postinit, Build, and App stages” and an old work order beginning with the supposedly open Coordinator question | [§6.6](../model.md#66-model-reconciliation-and-first-version-boundaries): App is not a stage; §4.1 already defines the first-version Coordinator | Stages are separated from App; the work order is replaced by references to domain open questions and the active responsibility allocation |
| Mesh / App, §7.1 | “Assigned roles” are published without qualifying them as descriptive responsibilities | [§4.1](../model.md#41-app-responsibilities): Executor and Interaction follow actual work; separate assignment is not mandatory | States performed responsibilities and actual participation |

## Other Editorial Inconsistencies

- §5.2 still used the name Performance Profiles even though §5.4 had abandoned mandatory universal modes. It was replaced with supported Line requirements and policies.
- Gecko / Axis, §3.5 described Mesh requirements on Axis results as still undefined. It now states that Mesh / App, §2.2–2.3 and §8 define them; domain schemas and methods remain open.
- Links to the moved work plan and renamed main document were fixed; a self-link labeled “Original Russian version” was removed.
- The illustrative Zenoh subscription key was corrected; Rust API map links using `latest` were changed to the stated version 1.10.1.
- The change history is explicitly identified as history containing superseded decisions. References to earlier Build Plan, App serialization, and performance profiles in historical entries are not contradictions of the active text and were not rewritten.

## Result

Remaining fragments of earlier revisions were aligned with already accepted rules. This review left no confirmed outdated-text conflicts requiring a new architectural decision. No new requirements, mechanisms, or additional conditions for finalizing 1.0.0 were introduced.
