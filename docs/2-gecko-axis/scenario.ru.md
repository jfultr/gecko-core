# Gecko / Axis: предварительные проверки и запрос клиента

[Модель Gecko / Axis](model.ru.md) · [Требования Mesh / App](../1-mesh-app/lower-level-requirements.ru.md) · [Цикл разработки](../development-cycle.ru.md)

**Статус:** сквозной сценарий для проработки контрактов D2 версии 1.0.0. Он показывает применение правил [Mesh / App, §2.2–2.3 и §8.2](../1-mesh-app/model.ru.md) и [Gecko / Axis, §3](model.ru.md); пример не вводит новых требований. Названия проверок ниже условны.

## Ход сценария

1. Пользователь запускает один Gecko. Gecko начинает предварительную проверку обнаружения Devices как обычный запуск Axis по [общим правилам исполнения и управления](model.ru.md#34-предварительные-axis-и-цепочки-проверок). У запуска есть собственная идентичность и Operation Report; контекст сохраняет автоматическое инициирование при старте Gecko. Состояние Gecko показывает, что сейчас идёт работа Axis.
2. Проверка находит Device и публикует его до собственного завершения. Эта находка даёт основание запустить следующую проверку свойств или доступа к найденному Device. Клиент может видеть найденный Device, пока следующая проверка ещё выполняется; находка сама по себе не подтверждает пригодность Device для конкретной обработки.
3. Клиент подключается после начала работы Gecko. Он получает уже доступные сведения и последние доступные отчёты запусков Axis, затем наблюдает новые результаты. Отсутствие текущей работы Axis не считается доказательством полноты сведений.
4. Для своей задачи клиент вызывает отдельный Axis с конкретным предметом и параметрами, без создания App. Gecko принимает корректный запрос и возвращает идентификатор запуска и адрес наблюдения либо отклоняет запрос с причиной. Потеряв ответ о принятии, клиент повторяет тот же запрос с тем же `request_id` и получает прежний запуск без второго выполнения.
5. Во время проверки Axis сообщает прогресс и частичный результат. Если обнаружен блокер, требующий внешнего исправления, запуск завершается с `state: failed`, сохраняя блокер и уже полученные сведения. Завершение этого запуска не означает, что Gecko всё ещё выполняет Axis. После исправления клиент явно отправляет новый запрос с новым `request_id`; Gecko создаёт новый запуск, а прежний результат остаётся отличимым от нового.

## Что должно быть наблюдаемо

- Состояние Gecko отвечает на вопрос, идёт ли сейчас работа Axis; оно не служит оценкой готовности App.
- У каждого запуска Axis различимы предмет, параметры, прогресс, частичный и итоговый результат, блокеры и актуальность полученных сведений.
- Клиенту доступны уже опубликованные сведения независимо от того, когда он подключился и завершилась ли текущая работа Axis.
- Повтор принятого запроса не запускает проверку повторно; новая проверка после изменения условий имеет новую идентичность.

## Вариант: пользователь меняет текущую работу

Клиент подключается во время предварительных проверок, запрашивает отмену одного из запусков и запускает дополнительную цепочку. Для этих действий используется общий интерфейс управления запусками Axis. Отчёты отражают фактическое состояние соответствующих запусков, а состояние Gecko — текущую работу с учётом изменений. Особая стадия завершения предварительных проверок не возникает. Инициатор каждого запуска остаётся различимым в его контексте.

Вариант не предполагает мгновенной отмены: распространение отмены на дочерние запуски, обращение с частичными результатами и конфликты ресурсов требуют дальнейших решений.

Конкретные предварительные проверки, условия вызова дочерних Axis, формат состояния Gecko, ключи Zenoh и политика хранения определяются предметными контрактами и проверяются на обратном проходе. Наличие блокера не превращается в общий запрет для клиента использовать уже известные сведения или запросить другую проверку.
